# Independent Tier-1 requirement traceability

The only source material used is `.scratch/vita4611_tier1.md`, `.scratch/standards/ipmi.txt`, `.scratch/standards/fru.txt`, and `TRANSPORT.md`. VITA pages are printed page numbers. References labeled IPMI or FRU use the printed page numbers of the respective text. No implementation sources, reference vectors, or adapter implementation are used.

Run `python tools/conformance/run_conformance.py --transport emu --report tools/conformance/results.md`, optionally with `--port N`. Other transport names are passed unchanged to `adapter.connect(transport, port)` as specified in `TRANSPORT.md`. Supply the separately authored `adapter.py` beside the runner. Only the documented Target methods and metadata, plus the adapter framing/checksum helpers and NoResponse exception, are used. A live target has not been exercised during authorship.

The registry has one stable ID per testable requirement/aspect. Parameterized command rows produce independent functions with cited docstrings and separate report entries. Related clauses defining one observable behavior share a row; physical and conditional behaviors which cannot be established through Target have individual NOT-TESTABLE rows. Requirements on the chassis manager or higher tiers are outside the Tier-1 IPMC scope. Recommendations are informational and never cause a mandatory conformance failure. Coverage is limited to the supplied extract; it is not a claim about omitted full-standard clauses.

PASS establishes the described bus observation under current conditions. FAIL includes observed frames in both console output and the optional Markdown report. NOT-TESTABLE includes a specific reason; it never counts as PASS. Rows labeled CONDITIONAL may produce NOT-TESTABLE for single-bus transports, absent optional features, missing bus-fault controls, unavailable readings, changing SDR population, initialization/update modes, or temporarily busy resources. Run on a quiet bus with a stable sensor/FRU population. Disabled or physically faulty management paths cannot establish normal functional behavior. Tests do not assume same-bus responses. Reset tests require the emulator transport and invalidate cached inventory. Exit status is 1 for any FAIL and 0 otherwise; the summary and report distinguish incomplete coverage.

Every Target.request has retries=0 and its own 250 ms timeout; adapter STOP-to-STOP elapsed_ms must be finite and at most 227 ms. This includes error, write, cleanup, partial-read and duplicate requests. Raw send_frame/receive probes have only a capture window; their lack of STOP timestamps is explicitly NOT-TESTABLE. Normal sequences are not reused within the five-second T9 interval. Deliberate duplicate tests reuse the exact sequence and command data within that interval.

FRU offsets honor byte or word access, while transfer counts describe returned data bytes. Readers accept short positive transfers and reconstruct overlapping word reads without assuming alignment of the final byte. Inventory and SDR requests use small chunks; no test assumes an entire SDR fits in one response. A reservation protects nonzero-offset SDR reads, record IDs are discovered rather than assumed consecutive, and all records are followed to next ID FFFFh.

All routine write probes transmit original bytes read from a checksum-validated target image. They do not manufacture arbitrary contents or alter checksums. Each write-capable test has finally cleanup: restore any differences to the saved full image and verify byte-for-byte equality. The primary and duplicate write tests also explicitly write the original header back. Protected storage returning 80h is accepted; partial writes are permitted by IPMI and counts are checked. A restoration failure stops subsequent tests. An already invalid FRU image is reported by the read checks and withheld from write probes. No test asserts NVMRO, modifies an unknown optional protection mask, or exercises payload activation. Same-value writes establish command layouts and current protection responses; they cannot prove physical programming occurred or internal execution count.

The supplied IPMI text permits FFh or a device-specific unspecified error for generic error conditions (section 5.3, pp.71-72). Such alternatives are accepted only where a particular completion code is not mandatory. Explicit VITA C1h/C9h/CCh and Write FRU Data 80h requirements retain their prescribed values. Error responses may truncate following data, but group-extension identifiers must remain (IPMI section 5.3.1 p.71). Reserved response bits documented as ignore-on-read are ignored; fields explicitly required to return fixed values are checked. Optional commands are never required to be absent: C1h is a compliant unsupported result, while supported commands are checked only where the supplied texts define their behavior.

## Specification decisions for review

1. **Mandatory sensor-number command:** Rule 6.2-2 p.123 says supported sensors shall be reported by Get Mandatory Sensor Numbers; Table 10.1.2-1 pp.178-179 marks it optional for Tier-1. The suite accepts C1h as an optional absence and reports NOT-TESTABLE. If present, fixed numbers, SDR agreement and the M0 D3h condition (Rule 4.1.5.4.1-10 p.55) are checked. Decide which provision governs the Tier-1 profile.
2. **2022 approval revision:** Section 10.1.3.1 pp.183-184 encodes the two-digit approval year in reversed-nibble BCD, while note 2 discusses earlier encodings. The suite requires 22h for a claimed 2022 target; decide whether any earlier revision advertisement should be accepted for an otherwise updated controller.
3. **Generic errors:** IPMI section 5.3 pp.71-72 allows FFh/device-specific unspecified errors unless an exact code is required. The suite accepts C6h/C7h for truncated requests, C7h/C8h for excess length, and C9h for out-of-range fields, with unspecified alternatives. Reserved-field error classification is not always fixed; explicit unsupported Set IPMB State parameters still require CCh (Rule 4.1.1-14 p.31). A stricter profile must be identified separately.
4. **Duplicate writes:** Observation 4.1.1-6 p.30 requires retained sequence on retries. IPMI Table 5-2 p.70 permits CFh when the original duplicate response cannot be returned; the explicit duplicate event-logging suppression text is in IPMI section 16.3 p.246 and does not establish an arbitrary FRU write execution counter. The suite tests safe repeated write replies, accepts legal duplicate errors, and marks internal no-reexecution NOT-TESTABLE. Decide whether an additional contractual exactly-once rule is intended and provide an observable safe side effect if so.
5. **Failure versus silent loss:** Rule 4.1.1-7 p.28 applies when transmission is unsuccessful. TRANSPORT.md only promises that bus_down loses frames, without defining whether the transmitter sees a failed acknowledgement. The suite checks alternate-bus delivery when available; absence of captured delivery under silent loss is inconclusive. The failed physical attempt itself is NOT-TESTABLE. Decide the required fault-injection semantics.
6. **Response-bus affinity:** Rule 4.1.1-6 p.28 requires alternation when both buses are operational and enabled; no same-bus response rule is present in the supplied extract. Requests may arrive on either bus and responses are accepted from either. The bench must capture both implemented enabled buses to test this.
7. **Site values:** Rule 4.1.4.3-3 p.43 gives the front-module site number, Rule 4.1.4.3-5 permits zero when unknown, and the chassis table footnote p.44 uses zero for another purpose. The suite accepts unknown zero and checks the returned hardware/site relation only for the identified front-module site type; unknown physical-address lookup prerequisites produce NOT-TESTABLE.
8. **Optional command detail:** The extract explicitly omits much optional material (reading notes), including the write-protection request/response tables in sections 10.1.3.34-36 pp.217-220. It cannot independently establish valid masks, protection getter layout, all fan/indicator/power/mode operations, or full bridge firewall semantics. These conditional requirements are listed as NOT-TESTABLE rather than guessed.
9. **Fault diagnosis timing and hardware stimuli:** Section 9.3 pp.167-170 defines isolation/fault handling but supplies no persistent-error timer in the extract. Bus-loss injection is not an electrical clock/data fault. Diagnostic timing, reset-held isolation, NVMRO causation and sensor threshold stimuli require additional bench interfaces.
10. **Bus speed:** Rule 4.1.1-4.3 p.28 requires STANDARD at startup; Table 3.3-1 pp.24-25 adds acceptance of the optional speed byte. The suite checks the currently advertised speed byte and startup sensor state, permits either advertised maximum frequency, and does not demand optional FAST operation from Tier-1. Electrical speed cannot be measured through Target.

No target-specific module identity, enterprise number, text field content, optional MultiRecord presence, reset-type sensor number, optional command presence, or additional standard/OEM SDR type is hard-coded as an expectation.
